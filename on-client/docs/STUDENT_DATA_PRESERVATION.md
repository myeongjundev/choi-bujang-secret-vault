# 학생 데이터 보존·백업·복원 계획

22단계 인수인계를 위한 계획이다. 이번에 실제로 수행한 것은 소스와 문서의 Git 보존·새 clone·시험·로컬 기본/예제 실행이다. 운영 DB 백업·복원이나 앱 자격 이전을 실행했다고 주장하지 않는다.

## 보존 대상과 범위

| 대상 | 보존·백업 방법 | 현재 확인 |
| --- | --- | --- |
| 학생 소스·시험·문서 | GitHub main의 커밋과 새 로컬 clone에 보존. 제출 40자리 해시를 상황실·작업 기록에 남김 | 실제 clone과 같은 소스의 38개 시험 확인 |
| 기존 1~12단계 자료실 코드·설정·성취 기록 | 기존 경로를 그대로 보존. 새 on-client 작업으로 초기화하지 않음 | 이번 작업 전 ce008ff와 비교해 기존 src/api/public/설정/의존성 파일 차이 없음 |
| 기존 자료실의 실제 학생 DB 자료 | 운영 담당자의 공식 백업 기능과 접근 제한된 보관 정책 사용. Git·제출 ZIP에 내용 포함하지 않음 | 기존 DB에 새 요청·초기화·삭제·복원 미실행. 백업 생성·보관 상태는 미확인 |
| native 호스트·앱 승인·기기 자격 | 공식 보관함·재승인 절차 사용. 다른 PC에 개인키나 평문 자격을 복사하지 않음 | 새 clone에 .env를 복사하지 않았고 두 위치에서 파일 없음 확인. 실제 자격 이전은 미실행 |
| on-client에 표시되는 기록·도움정보 | 원천이 보관한 본인 범위 자료를 재조회. 화면 표시를 영구 원천 백업으로 사용하지 않음 | 예제 자료와 로컬 진단만 확인 |

## 소스 복원과 검증 순서

1. 원래 폴더를 보존하고 현재 변경과 제출 커밋을 확인한다. 기존 폴더에 덮어쓰기·reset·clean을 하지 않는다.
2. STUDENT_GUIDE.md처럼 새 빈 폴더에 clone한다. 제출한 동일 커밋을 대상으로 하며 다른 브랜치·과거 통과 커밋을 섞어 최종 성공으로 세지 않는다.
3. npm 문법 검사와 학생 시험 38개를 실행한다. 실행 모듈 Git 객체와 제출본을 대조한다. 설정 없이 기본 실행의 연결 없음, 별도 예제 실행의 예제 표시를 확인한다.
4. 운영 설정이 필요한 기능은 담당자가 제공한 본인 프로젝트의 공식 설정·승인 절차로 복구한다. 값이 없으면 기다림(UNV)이며 임의 값으로 대체하지 않는다.
5. 앱을 종료·재시작하고 새 판정·기록을 조회한다. 이전 화면의 성공 표시만으로 복구됐다고 판단하지 않는다.

소스 clone·문법·시험·기본/예제 실행·재시작은 이번 새 폴더에서 수행했다. 운영 설정 복구와 실제 원천 재연결은 수행하지 않았다.

## 실제 학생 DB의 백업·복원 계획 · 미실행

1. 담당자가 백업 시각·대상 DB·보관 기간·권한·복구 지점을 확인한다. 학생 자료 본문을 채팅·로그·Git에 남기지 않는다.
2. 복원이 필요한 범위와 소유자를 확인하고, 운영자가 제공한 별도 검증 환경에서 백업의 읽기·복구 가능성을 먼저 확인한다. 기존 DB를 초기화하는 SQL을 재실행하지 않는다.
3. 기존 자료실의 단일 자료 복구 기능은 현재 코드의 소유자·범위·버전·해시·요청 승인 검증을 따른다. 앱 화면이나 문서가 실제 기기 승인·원천 권한을 대신하지 않는다. 필요한 운영 승인 연결이 없으면 복구를 진행하지 않는다.
4. 복구 후 허용된 본인 범위에서 자료 ID·버전·개수·기대 결과와 감사 기록을 대조하고, 정상 접근과 타인 접근 거부를 확인한다. 실패하면 성공으로 기록하지 않고 확인된 복구 지점으로 담당자가 대응한다.

위 DB 절차는 계획이며 이번에는 운영 백업 생성·복구·감사 확인을 실행하지 않았다. 현재 운영 엔진·서명·기기 결합·집행 연결이 미확인인 제한은 그대로 남는다. 새 clone과 예제 재시작은 운영 DB 복구 검증이 아니다.
